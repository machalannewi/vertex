# Sanity content model, standalone Studio, and server read data layer

## Goal

Stand up the Vertex content model (course, module, lesson, instructor, category) in a **standalone Sanity Studio workspace**, and a **server-only read client + data layer** in the Next.js app that fetches it. No pages, no search, no video pipeline, no progress tracking — those are separate tasks.

## Decision: split into two workspaces now

AGENTS.md §5 and the sanity-best-practices skill both say embedded Studio is legacy/not recommended for new projects (slower builds, no auto-update, no TypeGen watch mode) and require standalone `studio/` + `web/`. **Confirmed with user: doing the restructure now** rather than deferring it, since building the schema on top of the embedded setup would mean redoing this later anyway.

## Content model

Fixed by AGENTS.md §8; field-level choices below are mine.

- **category** (document, icon `TagIcon`): `title`, `slug`, `description`, `icon` (string, `options.list` of a curated lucide-react icon name set matching what the UI already imports in `course-card.tsx`, e.g. `BarChart2`, `Code`, `Database`, `Layers`, `Palette`, `Cpu`, `LineChart`) — search result cards need "course (name and icon)", and the icon lives on category since it's the shared taxonomy.
- **instructor** (document, icon `UserIcon`): `name`, `slug`, `photo` (image, hotspot, required alt text), `expertise` (array of strings, min 1), `bio` (text).
- **lesson** (document, icon `PlayIcon`): `title`, `slug`, `videoUrl` (url, http/https), `posterImage` (image, hotspot, required alt), `duration` (number, seconds — not a display string, so it can drive the video player's start-seconds math and clip-length formatting later), `freePreview` (boolean, default false), `studentCount` (number, default 0), `notes` (Portable Text array), `keyPoints` (array of strings, min 1), `proTip` (text, optional), `resources` (array of `resource` objects: `type` string list, `title`, `description`, `url`). No `course` back-reference, per spec — derive via reverse lookup.
- **module** (object, not a document, icon `DocumentsIcon`): `title`, `summary`, `lessons` (array of references to `lesson`, min 1, `unique()`). Lives only inside `course.modules`.
- **course** (document, icon `BookIcon`): `title`, `slug`, `summary`, `coverImage` (image, hotspot, required alt), `level` (string list: Beginner/Intermediate/Advanced, radio), `price` (number, min 0), `popular` (boolean, default false), `studentCount` (number, default 0), `outcomes` (array of `learningOutcome` objects: `icon` string, `title`, `description` — the "what you'll learn" list), `instructor` (reference), `category` (reference), `modules` (array of `module` objects, min 1).
- Module/lesson numbers (`Module 5`, `Lesson 5.1`) are never stored — derived from array position in `numbering.ts`.

All slugs: `source: 'title'` (or `'name'` for instructor), `maxLength: 96`, required, validated lowercase-hyphen via the standard custom rule from the schema skill.

## Data layer (`web/src/sanity/lib/`)

- `client.ts`: `import 'server-only'` at the top so an accidental client-component import fails the build instead of leaking the token to the browser. Reads `SANITY_API_READ_TOKEN` (new, server-only env var) and configures the client with it; `useCdn: true`.
- `queries.ts`: `defineQuery` constants — `ALL_CATEGORIES_QUERY`, `CATEGORY_BY_SLUG_QUERY`, `ALL_INSTRUCTORS_QUERY`, `INSTRUCTOR_BY_SLUG_QUERY`, `ALL_COURSES_QUERY`, `COURSE_BY_SLUG_QUERY`, `LESSON_BY_SLUG_QUERY`, `COURSE_FOR_LESSON_QUERY` (reverse lookup: `*[_type == "course" && references($lessonId)][0]{...}`, fetches modules/lessons so `data.ts` can compute position — GROQ can't return "the index of the match" directly).
- `data.ts`: thin async wrappers per entity — `getAllCategories`, `getCategoryBySlug`, `getAllInstructors`, `getInstructorBySlug`, `getAllCourses`, `getCourseBySlug`, `getLessonBySlug`, `getCourseAndPositionForLesson(lessonId)` (returns course title/slug, module title + index, lesson index, using `numbering.ts` to format labels). No catalog/search-specific projections yet — those are added when the catalog and search pages are actually built, per AGENTS.md's "build nothing beyond what's asked."
- `numbering.ts`: `getModuleLabel(moduleIndex)` → `"Module N"`, `getLessonLabel(moduleIndex, lessonIndex)` → `"Lesson N.M"`.
- Types come from TypeGen (`web/sanity.types.ts`, generated from `studio/schemaTypes` + `web/src/sanity/lib/queries.ts`) — no hand-written duplicate types.

## Requirements

- Two independent workspaces, each with its own `package.json`/`node_modules`; no npm/pnpm workspace tooling needed at root (per skill: optional, not required).
- Dataset stays private; the read token never reaches the browser (`server-only` import + no `NEXT_PUBLIC_` prefix).
- Schema uses `defineType`/`defineField`/`defineArrayMember` throughout, an icon on every document and object, and the deprecation-safe patterns if any field needs to change later.
- `module` stays an embedded object, never a document. `lesson` never stores its parent course.

## Security considerations

- `SANITY_API_READ_TOKEN` only read inside `web/src/sanity/lib/client.ts`, guarded by `import 'server-only'`.
- Studio's own dataset write access relies on the Studio user's Sanity login/role, not a token baked into the app — no write token exists yet (progress-write token is a future task).
- `.env.local` in both workspaces stays gitignored; only `.env.example` files are committed, with placeholders, never real project IDs beyond what's already public in git history.

## Acceptance criteria

- `studio/` runs standalone (`npm run dev` inside `studio/` → Studio at `localhost:3333`) showing Course, Lesson, Instructor, Category in the document list, with Module/Outcome/Resource editable as nested objects inside Course/Lesson.
- `web/` builds and type-checks with the studio route gone and no reference to `sanity.config.ts`/embedded Studio remaining.
- `web/src/sanity/lib/data.ts` functions compile against generated TypeGen types and return `null`/`[]` safely against an empty dataset (no runtime errors).
- No client component or browser bundle references `SANITY_API_READ_TOKEN` or imports `client.ts` in a way `server-only` would reject.

## Checks to run

- In `web/`: `npm run lint`, `npx tsc --noEmit`, `npm run build`.
- In `studio/`: `npx sanity build` (offline, validates schema/config compile without requiring login), plus `npx sanity schemas extract --force && npx sanity typegen generate` to produce `web/sanity.types.ts`.
- Studio deploy (`npx sanity deploy`) and `npx sanity cors add http://localhost:3000 --credentials` require an interactive Sanity login — left as a manual step for you, listed below.

## Manual test steps

1. `cd studio && npm install && npm run dev` — confirm Studio loads at `http://localhost:3333` with Course/Lesson/Instructor/Category types visible.
2. In Studio, create one Category, one Instructor, one Lesson, then one Course referencing them with one Module containing that Lesson. Publish all four.
3. `npx sanity login` then `npx sanity deploy` (from `studio/`) — required before the Context MCP can ever serve this dataset (future search task).
4. `npx sanity cors add http://localhost:3000 --credentials` (from `studio/`) so `web/` can read the dataset.
5. Add a Viewer-role token from [sanity.io/manage](https://sanity.io/manage) to `web/.env.local` as `SANITY_API_READ_TOKEN`.
6. `cd web && npm install && npm run dev` — app should still start with no studio route (visiting `/studio` now 404s, which is expected — Studio lives at `localhost:3333`).
7. Temporarily add a one-off `console.log(await getAllCourses())` in a server component (e.g. the homepage) to confirm it returns your published course with the expected shape, then remove it.
